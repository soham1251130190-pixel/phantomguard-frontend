# PhantomGuard — `generate/` (Pillar 2: Attack Simulation)

Synthetic fraud transaction generator for the Mastercard Innovation
Challenge submission. This is Member 2's module — it turns an
`attack_type` into realistic, labeled transaction data that Member 3's
detection model trains on.

## Why it's built this way

The brief said: *"design the transaction generator so `attack_type` is a
parameter, allowing us to add more attack types later without rewriting
the whole generator."* Concretely:

- **`config.py`** is the only place attack types are declared (`ATTACK_REGISTRY`).
  It's a dict, not code — adding attack #11 is one entry here.
- **`pattern_injector.py`** has one small function per attack type that
  mutates a baseline transaction into that attack's signature. It never
  touches the engine.
- **`transaction_sim.py`** is generic: `generate_transactions(attack_type, n)`
  looks the attack up in the registry, builds a realistic baseline
  transaction, and calls the matching injector. It has **zero
  attack-specific branching** — the file doesn't change when attack #11
  ships.

So today it's 10 generators; scaling to the full 47+ vision in the
PhantomGuard doc is additive, not a rewrite.

## Files

| File | Purpose |
|---|---|
| `config.py` | Attack type registry (10 types) — the extension point |
| `schema.py` | Full column dictionary (56 columns): dtype, feature block, ML role |
| `fake_data.py` | Curated name/geo/merchant/device reference pools (no internet dependency) |
| `persona_generator.py` | Builds a synthetic *user* (identity + behavioral history) per one of 4 profiles |
| `transaction_sim.py` | The generic engine — `generate_transactions(attack_type, n)` |
| `pattern_injector.py` | One fraud-signature function per attack type |
| `fidelity_checker.py` | Sanity checks: no constant columns, per-attack separability, NaN patterns |
| `generate_dataset.py` | CLI entry point |
| `export_data_dictionary.py` | Dumps `schema.py` to CSV/Markdown for the Solution Walkthrough doc |

## The 10 initial attack types

| attack_type | Category | GenAI capability | Persona profile used |
|---|---|---|---|
| `synthetic_identity_fraud` | identity | text_generation | new_thin (thin-file account) |
| `account_takeover` | access | credential_stuffing_automation | established_trust |
| `ai_phishing` | social_engineering | text_generation | mule_or_victim |
| `voice_cloning_fraud` | social_engineering | voice_synthesis | mule_or_victim |
| `deepfake_identity_fraud` | identity | video_synthesis | new_thin |
| `synthetic_document_fraud` | document | image_generation | new_thin |
| `payment_diversion_invoice_fraud` | social_engineering | text_generation | established_trust |
| `merchant_fraud` | merchant | text_generation | normal |
| `refund_fraud` | merchant | text_generation | normal |
| `coordinated_multi_account_fraud` | network | identity_generation_at_scale | new_thin (ring of accounts) |

Each attack was designed around **how it actually shows up in payments
data**, not just a random label — e.g. `account_takeover` mutates
device/IP/login-anomaly fields on an *established* account, while
`synthetic_identity_fraud` mutates KYC/document/credit-history fields on
a *brand-new* account and adds a bust-out amount spike. This is what
gives the "Defend" model (Member 3) actual separable signal to learn per
attack type, instead of one generic "high amount = fraud" shortcut.

## Data schema (56 columns)

Organized into blocks that map directly onto the "Feature Engineering
(200+ features)" categories in the PhantomGuard doc:

- **transaction-level** (21 cols): amount, channel, merchant, device, geo, velocity, timing
- **user-level** (13 cols): account age, KYC level, credit band, history, behavioral score, MFA
- **network-level** (5 cols): shared device/IP counts, graph cluster id, beneficiary patterns
- **GenAI-specific** (6 cols): text/voice/video/document/image authenticity & LLM-generation scores
- **attack-specific auxiliary** (3 cols): refund counters, structuring score
- **labels** (6 cols): `is_fraud`, `attack_type`, `attack_category`, `genai_capability`, `fraud_severity` (soft/graded label), `ground_truth_source`

Full descriptions: `data/data_dictionary.md` (generated by `export_data_dictionary.py`).

**Important for training:** `schema.FEATURE_COLUMNS` gives the exact
list of columns that are safe to use as model input — labels and key
columns are excluded automatically, so Member 3 can do
`X = df[FEATURE_COLUMNS]` without hand-picking columns or risking label
leakage.

GenAI feature columns are intentionally **sparse/NaN** outside their
relevant channel (e.g. `voice_authenticity_score` is only populated for
phone-channel rows) — that mirrors production, where you only run
voice-liveness models on voice-channel events. Models should either use
NaN-aware trees (XGBoost handles this natively) or an explicit
"feature applicable" flag.

## Quickstart

```bash
pip install -r requirements.txt

# Full balanced training set: 1,500 rows per attack type + 15,000 legitimate (30k total, 50% fraud)
python generate_dataset.py --mode all --n_per_attack 1500 --out data/phantomguard_synthetic_dataset.csv

# Realistic, imbalanced holdout for honest evaluation (0.6% fraud rate, mimics live traffic)
python generate_dataset.py --mode realistic --n 40000 --out data/phantomguard_realistic_holdout.csv

# One attack type only (fast iteration for Member 3)
python generate_dataset.py --mode single --attack_type voice_cloning_fraud --n 3000 --out data/voice_cloning_sample.csv

# See all attack types
python generate_dataset.py --list
```

Every run prints a fidelity report: class balance, amount distributions
by class, and — per attack type — the single most discriminative
feature and its standardized effect size vs. legitimate traffic. That
last number is a quick smell test: too low (~0) means the attack isn't
learnable; too high (>15) usually means an accidental leak.

## Train / evaluate split recommendation

Use **two separate generated datasets**, not a random split of one:

1. `--mode all` (balanced) → training set. Balanced classes make the
   model actually learn each attack's signature instead of just
   predicting the majority class.
2. `--mode realistic` (imbalanced, ~0.6% fraud, attack mix weighted by
   `severity_weight`) → evaluation set. This is what makes your F1 /
   false-positive numbers in the Solution Walkthrough credible — a
   model evaluated on a 50/50 set will look far better than it would in
   live payments.

## Blended / chained attacks

Real fraud often chains techniques (phishing harvests a credential, which
is then used for account takeover). `attack_type` accepts **any
combination** of registered types — no extra registration needed:

```python
from transaction_sim import generate_transactions

# a row carries BOTH signatures at once: high phishing-text-similarity
# AND low device-trust/high login-anomaly
df = generate_transactions(["ai_phishing", "account_takeover"], n=1500)
```

or from the CLI with `+`:

```bash
python generate_dataset.py --mode single \
    --attack_type ai_phishing+account_takeover --n 1500 \
    --out data/blended_phishing_ato.csv
```

What happens under the hood:
- Both injectors run on the same row, in a randomized order per row (so
  which one "wins" on any overlapping field varies across rows instead
  of being a fixed artifact of registry order).
- `attack_type` is stored as `"ai_phishing+account_takeover"`;
  `attack_category` and `genai_capability` are similarly joined
  (de-duplicated) — so you can still filter to `attack_type.str.contains("account_takeover")`
  to catch it whether it's standalone or blended.
- `fraud_severity` is a probabilistic OR of the two components'
  severities (`1 - (1-s1)(1-s2)`), not just whichever injector ran last
  — a blended attack should generally read as *more* severe than either
  half alone, and this reflects that instead of overwriting it.
- A new label column, `is_blended_attack` (bool), flags these rows
  explicitly, so Member 3 can train/evaluate on pure and blended attacks
  separately if useful (e.g. "does the model still catch it when it's
  chained, not just standalone?").

`data/phantomguard_synthetic_dataset.csv` now includes 5 example blended
combos (400 rows each) alongside the 10 pure attack types, so the
detection model sees at least some chained examples out of the box.
The fidelity checker (`fidelity_checker.py`) treats blended types as
just another `attack_type` value — it'll report their separability
from legitimate traffic the same way it does for pure types.

## Extending to attack #11+

1. Add an entry to `ATTACK_REGISTRY` in `config.py` (id, category,
   genai_capability, channel bias, severity weight, injector name).
2. Write the matching `inject_<name>(rng, persona, txn)` function in
   `pattern_injector.py` — mutate the 5-10 fields that actually carry
   that attack's real-world signal, set `fraud_severity`, return `txn`.
3. Register it in `pattern_injector.INJECTORS`.
4. (Optional) Add a persona profile mapping in
   `transaction_sim.ATTACK_PERSONA_PROFILE` if none of the 4 existing
   profiles (`normal`, `new_thin`, `established_trust`,
   `mule_or_victim`) fit.

No other file changes — `transaction_sim.py`, `generate_dataset.py`, and
`fidelity_checker.py` are all attack-agnostic.
